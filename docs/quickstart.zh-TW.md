# Build Center 快速上手 ⚡

> 目標:5 分鐘看完,馬上會用。完整參考請看 [README.md](./README.md)。

---

## 這是什麼(30 秒版)

把專案打包成「可以直接執行的東西」的平台,三種類型:

| 類型 | 做什麼 | 產出 |
|---|---|---|
| **後端** | 用 Nuitka 把 Python 編成執行檔 | 一個 binary(+ libs/) |
| **前端** | 用 npm/yarn/pnpm/bun build | 一包靜態檔 dist/ |
| **全端** | 先 build 前端,再把它包進後端 binary | 一個 binary |

每種都可以再選「要不要包成 Docker image」。

---

## 第一次使用

1. **註冊**:第一個註冊的人自動成為管理員、直接登入。之後註冊的人會進入「**等待審核**」,要管理員到「使用者管理」核准才能登入。
2. **登入後**會看到儀表板。沒有任務時,點 **「建立第一個任務」** 開始。

> 儀表板上半部是**建置健康度**:近 30 天成功率、每個專案最近 12 次的成敗、最常見的失敗原因。
> 如果最上方出現紅色的「**編譯環境降級**」橫幅,表示某個 Python 版本在伺服器上不可用 ——
> 選到它的話會靜默改用別的版本編譯,產出會在執行時壞掉。看到就先告訴管理員。

## 建立任務 —— 5 個步驟

跟著精靈走,每一步上方都有提示。**不確定的欄位保持預設、直接下一步就好。**

### ① 基本資訊(唯一必填頁)
- **專案名稱**:隨便取,給自己看的。
- **專案類型**:後端 / 前端 / 全端。
- **來源**:
  - **本機路徑** — 伺服器上已存在的目錄(需在 `/media/disk0/` 或 `/media/disk1/` 底下)。
  - **Git URL** — 貼上 repo 網址,系統自動 clone(token 由伺服器注入,**別把帳密寫進網址**)。選好分支/標籤後會自動讀取目錄與依賴群組。

### ② 後端設定(後端 / 全端才有)
- **進入點**:主程式,例如 `main.py`。
- **打包模式**:見下方「兩種模式怎麼選」。
- **依賴群組**:自動讀 `pyproject.toml` 的 `[dependency-groups]`,單選。典型用途:選不同平台的 PyTorch(rocm/cuda/cpu)。
- **進階設定**(可不動):CPU 並行數、強制納入套件、要一起打包的 source code 目錄、資料目錄、以及下方「進階選項速查」那幾個。

### ③ 前端設定(前端 / 全端才有)
- 按 **「自動偵測」** 會幫你帶入建置工具與輸出目錄。
- 可載入 `.env` 環境變數,build 時寫入、build 完還原。

### ④ Docker(選用)
- 不需要就保持「否」直接下一步。
- 純前端開 Docker = 包成 **nginx image**,可設 API 反向代理與下方的 nginx 旋鈕。

### ⑤ 確認 → 送出
送出後任務立刻排隊,自動跳到任務詳情頁看進度。

## 兩種打包模式怎麼選(後端)

| | **External(建議)** | **Full** |
|---|---|---|
| 第三方套件 | 放在執行檔旁的 `libs/` | 全部編進單一執行檔 |
| 編譯時間 | 快 | **非常久,8hr 起跳** |
| 適合 | 幾乎所有情況 | 真的要單一檔案交付時 |

**不確定就用 External。**

## 你會看到的「完整打包流」🆕

後端/全端任務送出後,任務詳情頁上方有一條**階段進度條**:

```
排隊 → 預檢 → 編譯 → 打包 → 驗證 → 完成
```

- **預檢**:編譯前先檢查「進入點存在 / 輸出目錄可寫 / .venv 在不在」。有問題**立刻擋下**,不用等老半天才發現打錯。
- **驗證(打包後)**:編完自動啟動一次 binary,確認**不會一開機就因為缺套件掛掉**。偵測到 `ModuleNotFoundError` 會把任務判**失敗**並告訴你缺哪個模組。
- 完成後出現 **「打包成果卡」**:產物大小、檔案數、SHA-256、驗證結果(✓綠勾 / ⚠警告 / ✗失敗)、耗時。

> 看到綠勾 ✓ = 真的能啟動,可以放心下載。

## 進階選項速查(後端,都可不動)

| 選項 | 預設 | 什麼時候調 |
|---|---|---|
| 縮小體積(anti-bloat) | 開 | 想要更小的執行檔(主要對 Full 有感) |
| 打包後驗證 | 開 | **建議保持開**;某些特殊 app 才需要關 |
| 產生編譯報告 | 關 | 遇到「執行時缺東西」想查誰被漏掉 |
| 強制納入套件「資料檔」 | 自動 | 執行時噴 `FileNotFoundError`、缺的是套件內建 json/憑證時,填套件名(例:`certifi, litellm`) |
| 強制納入套件 | 空 | Nuitka 偵測不到的動態 import(例:`litellm, openai`) |

## 純前端 + Docker 的 nginx 設定 🆕

開 Docker 的純前端任務,在 Docker 步驟可調(都可不動):

| 設定 | 預設 | 說明 |
|---|---|---|
| **上傳大小上限** | `0`(不限) | 上傳檔案出現 **413** 時調這個。例:`50m`、`1g` |
| **後端最久可以「不出聲」多久** | `300s` | 見下方說明 —— 這是最常被誤解的一個 |
| **串流模式** | 開 | LLM 逐字輸出(SSE)、長音檔上傳要開。關掉的話 nginx 會等後端整包回完才送出 |
| **gzip 壓縮** | 開 | 壓縮 CSS/JS,減少傳輸量 |
| **API Proxy 網址** | 空 | nginx 把 `/api` 反向代理到這個後端網址 |

### 逾時到底在算什麼(這題最多人踩)

它算的是「**後端最長一段沉默有多久**」,**不是**請求總共跑多久。每收到一點資料就重新計時。

| 你的後端 | 要不要調? |
|---|---|
| SSE / 逐字串流的 LLM | ❌ 不用 —— 每個 token 都會重置計時器 |
| **語音辨識、一次性回傳的 LLM** | ⚠️ 只有當最壞情況可能超過 300 秒才調大 |
| WebSocket 有心跳 | ❌ 不用 |
| WebSocket 沒有心跳 | ✅ 要 —— 必須大於最長的靜默期 |
| 大檔上傳 | ❌ 不用 —— 串流模式已讓資料持續流動 |

**為什麼 STT 特別容易中招**:上傳音檔 → 後端算很久、期間**完全不回傳任何東西** → 一次吐出結果。
計時器到期時 nginx 回 **504** 並切斷連線,但你的後端不知道,會繼續算完、把結果寫回一條沒人在聽的連線 ——
所以**後端日誌顯示成功、使用者卻收到 504**,很容易往「STT 服務不穩」的方向誤判。

> ⚠️ **如果容器外面還有一層公司的 nginx,那層有它自己的逾時。** 只改這裡沒用 ——
> 鏈上任何一層都會生效,以最小的為準。重建後若仍在**約 60 秒**斷掉,就是外層那道。
>
> 最穩的解法是讓後端在等待期間定期送資料(SSE 每 10 秒送一行 `: keepalive`),
> 這樣每一層代理都會同時被滿足,不需要去改任何設定。

> 工具支援:npm / yarn 直接可用;pnpm 走 corepack;bun 用 `oven/bun` 映像。**選哪個工具,Dockerfile 都會自動配好。**

## 完成之後

- **下載**:任務詳情頁或歷史頁的「下載輸出」→ 拿到 `.tar.gz`。編譯報告(若有開)也一起包在裡面。
- **重新打包**:任一任務按「重新打包」會帶著原設定回到精靈,改一改再送。
- **歷史**:History 頁可搜尋使用者、匯出 CSV;點進去看當時的設定與成果卡。

## 常見問題 / 排錯

| 症狀 | 多半是 | 怎麼辦 |
|---|---|---|
| 任務一開始就失敗、訊息提到「預檢」 | 進入點打錯 / 專案目錄不可寫(權限)/ 沒建 .venv | 照預檢訊息修;權限問題把專案目錄改成 build 帳號可寫 |
| 驗證失敗、說缺某個模組 | Nuitka 沒抓到動態 import | 把該套件填到「強制納入套件」,或改用 External,或關 anti-bloat 重試 |
| 執行時 `FileNotFoundError` 找資料檔 | 套件的非 .py 資料檔沒打包 | 把套件名填到「強制納入套件資料檔」 |
| 前端 Docker 上傳檔案 413 | nginx 上傳上限 | 把「上傳大小上限」設大(或 `0`) |
| Full 模式跑超久 | 正常,Full 本來就 8hr 起跳 | 改用 External |
| 任務一直卡著不動 | 可能在排隊等建置名額 | 看狀態列是否顯示「Queued」;有名額會自動開始 |
| 打包出來的服務出現 **504** | nginx 閒置逾時,不是後端當掉 | 見上方「逾時到底在算什麼」 |
| 註冊完卻登不進去 | 新帳號預設**停用**,需管理員核准 | 請管理員到 Users 頁把帳號改成啟用 |

## 失敗了怎麼辦

任務失敗時,詳情頁會直接告訴你三件事:

1. **失敗階段** —— 預檢 / 編譯 / 打包 / 驗證,先知道卡在哪一步
2. **自動診斷** —— 系統認得的失敗會直接說明原因與修法。有些還會附一顆按鈕
   (例如「改用自動偵測並重新建置」),按下去會帶著修正過的設定回到精靈
3. **關鍵錯誤行** —— 日誌裡最後出現的錯誤訊息

**即使系統認不出原因**,也一定會給你階段與錯誤行。看不懂的話,把那幾行連同任務連結貼給管理員就夠了 ——
不需要自己讀完整份日誌。

> 💡 **最常見的失敗是 Python 版本不符**:專案 `.venv` 裡的套件是用某個版本編譯的,
> 你卻選了另一個。現在填表時就會警告並提供一鍵修正,但如果你是手動指定版本,
> **選「自動偵測」幾乎永遠是對的**。

---

有問題先看任務的**建置日誌**(詳情頁右側),九成原因都在裡面。
